# A stated desire is not a build order

**"I want X", "I'd like X", "it would be nice if X" opens a design
discussion. It does not authorize building X.**

Between a question and an imperative sits a third thing: a wish. It names an
outcome and is silent on how to reach it. Acting on it means inventing the
design — tool, structure, file layout, naming — and handing it over as
finished work the user must now review or undo. The user never got to make the
decisions that were theirs.

## Not a build order

- "I would like to be able to X" / "I want X" / "it'd be nice if X"
- A list of desires, especially as bullets
- Answering a clarifying question — that advances the design, it does not end it
- Approving one fork ("yes, Karabiner") — that settles that fork and nothing else

## A build order

An imperative aimed at implementation, given after the approach is settled:
"build it", "go ahead", "do it", "implement that", "yes, that one".

## What to do with a wish

1. Name the real forks — choices that change the shape of the result.
2. Recommend one, with the reason, per [chase the ideal](chase-the-ideal.md).
3. Name what only the user can supply, and anything with a privacy or
   irreversibility consequence.
4. Stop. Wait for the build order.

Read-only investigation to inform the proposal is welcome — say that is what it
is. Groundwork that silently turns into edits is the failure this rule exists to
prevent.

## Provenance

A request for two global hotkeys — a Firefox tab and one Telegram chat. The
desire was stated as two bullets; the reply surveyed the machine, picked
Karabiner, chose a file layout, and was writing scripts when it was
interrupted. Nothing about the approach had been discussed.
